# TableTalk Recipe Sharing App - Project Plan and Technical Guide

## 1. Project Overview

TableTalk is a full-stack recipe-sharing application. It gives users a place to:

- Browse recipes stored in MongoDB.
- Search recipes by title, ingredient, or author.
- Open a complete recipe with ingredients and cooking steps.
- Publish a new recipe.
- Edit an existing recipe.
- Upload a recipe image through Multer and Cloudinary.
- Like and unlike recipes.
- Save and unsave recipes.
- Move through paginated recipe results.

The project is intentionally split into two independent applications:

```text
mini-project/
|-- frontend/     React and Vite browser application
|-- backend/      Express REST API and MongoDB integration
|-- Plan.md       This technical project guide
|-- README.md     Short setup and API reference
```

The frontend runs on port `5173` by default. The backend runs on port `5000` by default. MongoDB stores recipe documents, while Cloudinary stores uploaded image files.

## 2. Architecture

```text
Browser
  |
  | React Router pages and Fetch requests
  v
Frontend: Vite + React
  |
  | HTTP requests to /api/recipes
  v
Backend: Express
  |
  | Mongoose queries
  v
MongoDB Atlas / MongoDB

Backend image path:
Browser file
  -> FormData
  -> Multer memory buffer
  -> Cloudinary upload stream
  -> Cloudinary secure_url and public_id
  -> MongoDB Recipe document
```

The browser never talks directly to MongoDB. It sends HTTP requests to Express. The backend owns validation, database operations, image handling, and response formatting.

There is currently no authentication system. The frontend uses the string `you` as the current user identifier when toggling likes and saves. The API accepts any user identifier in the request body, so a real authentication layer can be added later without changing the recipe schema.

## 4. MongoDB Schema

The `Recipe` model stores documents shaped like this:

```json
{
  "_id": "ObjectId",
  "title": "Lemon Butter Pasta",
  "ingredients": ["Spaghetti", "Unsalted butter", "Parmesan"],
  "steps": [
    "Cook the pasta.",
    "Make the lemon butter sauce.",
    "Toss and finish with Parmesan."
  ],
  "cookingTime": 30,
  "imageUrl": "https://res.cloudinary.com/...",
  "imagePublicId": "tabletalk-recipes/abc123",
  "author": "Saran Hitrik",
  "likes": 18,
  "likedBy": ["you"],
  "savedBy": ["you"],
  "createdAt": "2026-10-16T...",
  "updatedAt": "2026-10-16T..."
}
```

Field behavior:

- `title`: Required trimmed string, maximum 120 characters.
- `ingredients`: Required array of trimmed strings.
- `steps`: Required array of trimmed strings.
- `cookingTime`: Required positive number. The route requires an integer.
- `imageUrl`: Required stored image URL. It can be a Cloudinary URL or an externally supplied URL.
- `imagePublicId`: Optional Cloudinary public ID used to identify the stored asset.
- `author`: Required trimmed string, maximum 60 characters.
- `likes`: Non-negative number. It is synchronized with `likedBy.length` by the like endpoint.
- `likedBy`: Array of user identifiers who liked the recipe.
- `savedBy`: Array of user identifiers who saved the recipe.
- `createdAt` and `updatedAt`: Added automatically by Mongoose timestamps.

Search index:

```text
title + ingredients + author
```

The `GET /api/recipes` route uses MongoDB `$text` search when the `search` query value is not empty.

## 5. REST API Contract

### `GET /api/health`

Health check used to confirm that Express is running.

Response:

```json
{ "status": "ok" }
```

### `GET /api/recipes?search=&page=1&limit=6`

Lists recipes.

Query parameters:

- `search`: Optional text search across title, ingredients, and author.
- `page`: Optional page number. Defaults to 1.
- `limit`: Optional page size. Defaults to 6 and is capped at 24.

Behavior:

1. Normalizes page and limit.
2. Builds an empty MongoDB filter or a `$text` filter.
3. Sorts newest recipes first by `createdAt`.
4. Skips previous pages.
5. Limits the result count.
6. Counts matching documents.

Response:

```json
{
  "recipes": [],
  "pagination": {
    "page": 1,
    "limit": 6,
    "total": 6,
    "pages": 1
  }
}
```

### `POST /api/recipes`

Creates a recipe. The frontend sends `multipart/form-data` so it can include either an image file or an image URL.

Text fields:

- `title`
- `author`
- `cookingTime`
- `imageUrl` (optional if an image file is provided)
- Repeated `ingredients` fields
- Repeated `steps` fields

File field:

- `image`: Optional image file, maximum 5 MB.

Flow:

1. Multer parses the multipart request.
2. The route normalizes single values and arrays into arrays.
3. If a file exists, Cloudinary receives it and returns `secure_url` and `public_id`.
4. The route places the Cloudinary URL into `imageUrl`.
5. The route validates all required values.
6. Mongoose inserts the recipe document.
7. The new recipe is returned with HTTP 201.

### `GET /api/recipes/:id`

Loads one recipe by MongoDB ObjectId. Returns HTTP 404 when the document does not exist.

### `PUT /api/recipes/:id`

Updates a recipe using the same text and file fields as `POST`.

Behavior:

- Loads the existing document first.
- If a new image is provided, uploads the new image to Cloudinary.
- If no new file is provided, keeps the previous image URL and public ID.
- Validates the updated payload.
- Runs `findByIdAndUpdate` with Mongoose validators enabled.
- Returns the updated recipe.

### `POST /api/recipes/:id/like`

Accepts:

```json
{ "user": "you" }
```

Behavior:

- Loads the recipe.
- If the user is already in `likedBy`, removes the user.
- Otherwise adds the user.
- Sets `likes` to the new `likedBy.length`.
- Saves and returns the recipe.

This makes the endpoint a like/unlike toggle.

### `POST /api/recipes/:id/save`

Accepts the same user payload:

```json
{ "user": "you" }
```

Behavior:

- Loads the recipe.
- Removes the user from `savedBy` if already saved.
- Otherwise adds the user.
- Saves and returns the recipe.

This makes the endpoint a save/unsave toggle.

## 6. Detailed Image Upload Flow

The upload flow begins in `RecipeForm`:

1. The user selects a local image in the file input.
2. React stores the `File` object in `imageFile` state.
3. On submit, the form creates a `FormData` object.
4. Text values are appended to the form.
5. Each ingredient and step is appended as a repeated field.
6. The image is appended under the field name `image`.
7. `createRecipe` or `updateRecipe` sends the FormData using Fetch.
8. Fetch does not manually set `Content-Type`; the browser supplies the multipart boundary.

On the backend:

1. `upload.single("image")` reads the file.
2. Multer stores the file in memory, not on the backend disk.
3. The route checks that Cloudinary configuration exists.
4. `uploadToCloudinary` creates an upload stream.
5. If `CLOUDINARY_UPLOAD_PRESET` exists, `unsigned_upload_stream` uses the configured unsigned preset.
6. If no preset exists, the code falls back to a signed `upload_stream` using the configured Cloudinary credentials and folder.
7. The in-memory file buffer is written into the Cloudinary stream.
8. Cloudinary returns metadata, including:
   - `secure_url`: HTTPS URL used by the frontend.
   - `public_id`: Cloudinary asset identifier.
9. The route stores `secure_url` in `imageUrl` and `public_id` in `imagePublicId`.
10. MongoDB saves only the URL and asset metadata, not the binary image.
11. Later recipe reads return the Cloudinary URL, which the browser loads directly from Cloudinary.

This keeps large image data out of MongoDB and lets Cloudinary handle image delivery.

## 7. Frontend Request Flows

### Browse flow

1. Browser opens `/`.
2. `Discover` reads `search` from the URL query string.
3. `useEffect` calls `getRecipes`.
4. Fetch calls `GET /api/recipes?search=...&page=1&limit=6`.
5. The response fills the recipe grid and pagination metadata.
6. Loading, error, and empty states are rendered based on request state.

### Search flow

1. User types an ingredient, title, or author into the search field.
2. Submit updates the router query string.
3. The effect runs again with the new search value.
4. The backend performs MongoDB text search.
5. Matching recipes render with the search phrase in the section heading.

### Detail flow

1. User selects a recipe card.
2. React Router loads `/recipes/:id`.
3. `RecipeDetail` calls `GET /api/recipes/:id`.
4. The response renders image, title, author, cooking time, ingredient list, and method.
5. Like, save, and edit actions are available from the detail page.

### Like/save flow

1. User clicks the heart or bookmark control.
2. The frontend sends the current local user identifier `you`.
3. The API toggles the matching array value.
4. The returned document replaces local recipe state.
5. The control updates its active state and count.

### Create/edit flow

1. User opens `/new` or `/recipes/:id/edit`.
2. Edit mode loads the existing recipe first.
3. Ingredients and steps are displayed as newline-separated text.
4. On submit, text is converted back into repeated multipart fields.
5. The backend creates or updates the MongoDB document.
6. The client navigates to the saved recipe detail page.

## 8. Database Save and Retrieve Behavior

### Saving a recipe

`POST /api/recipes` uses `Recipe.create(data)`. Mongoose validates required fields and schema constraints before inserting the document.

`PUT /api/recipes/:id` uses `findByIdAndUpdate` with:

```js
{ new: true, runValidators: true }
```

This returns the updated document and applies schema validation.

### Retrieving recipes

List retrieval uses:

```js
Recipe.find(filter)
  .sort({ createdAt: -1 })
  .skip((page - 1) * limit)
  .limit(limit);
```

The API performs the list query and `countDocuments` concurrently so the frontend receives both records and pagination information.

Single retrieval uses `Recipe.findById(id)`.

### Updating likes and saved users

Like and save operations load the document, modify the correct array, and call `save()`. This ensures the current document state is used when toggling.

## 11. Current Limitations and Next Improvements

The project is functional, but these areas are intentionally simple:

1. Authentication is not implemented. The client uses the fixed user identifier `you`.
2. Authorization is not implemented. Any caller who knows a recipe ID can call the edit endpoint.
3. Old Cloudinary assets are not deleted when a recipe image is replaced.
4. The backend error handler currently returns status 500 for unexpected errors instead of preserving provider-specific statuses.
5. The frontend uses external image URLs in the starter seed data.
6. There are no automated API or component tests yet.
7. Deployment configuration for a hosted frontend, backend, MongoDB, and Cloudinary environment still needs to be added.

Recommended next steps:

- Add user registration and login with session or JWT authentication.
- Protect edit, like, and save actions by authenticated user identity.
- Delete the previous Cloudinary `imagePublicId` after a successful replacement.
- Add request tests for search, pagination, validation, uploads, likes, and saves.
- Add a production `VITE_API_URL` configuration.
- Add deployment environment variables without committing secrets.
